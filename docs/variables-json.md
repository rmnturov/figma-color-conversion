# Экспорт и импорт цветов Variables

Штатный **Export modes** в проверенном P3-документе сохраняет RGB-числа переменной без преобразования в sRGB, но записывает `colorSpace: "srgb"`. Штатный **Import mode** переносит поддерживаемые RGB-числа без преобразования к профилю документа. Одинаковый JSON задаёт одинаковые числа в P3 и sRGB, но цветовая интерпретация этих чисел различается.

Практическая проверка выполнена **15 октября 2026 года**. Изучены 28 переменных исходного экспорта, 24 контрольные записи и пять опытов с единицами HSL в двух профилях. Итоговые документы содержат по 57 переменных и 57 связанных слоёв. [Отчёт, JSON и локальные `.fig`](../research/2026-10-15/variables-json/README.md) сохраняют данные для повторения.

## Табличный HEX и экспорт

Переменная `overlay-p3-hex` в таблице P3-документа показывает `#1D2D6B`. В штатном экспорте её `$value` имеет вид:

```json
{
  "colorSpace": "srgb",
  "components": [
    0.11372549086809158,
    0.1764705926179886,
    0.41960784792900085
  ],
  "alpha": 1,
  "hex": "#1D2D6B"
}
```

`components` совпадают с сохранёнными P3-каналами `29/255`, `45/255`, `107/255` с точностью float32. Преобразование P3 в sRGB дало бы примерно `[0.0942091, 0.1786137, 0.4355646]` и HEX `#182E6F`. Экспорт содержит другие числа, поэтому метка `srgb` не подтверждает такое преобразование.

У `overlay-css-oklch` таблица также показывает `#1D2D6B`, но экспорт содержит `[0.11302462965250015, 0.17683282494544983, 0.419991672039032]`. Сохранённые числа не восстановлены из табличного HEX. HEX скрывает точность, которая остаётся в переменной и JSON.

На 16 литеральных цветах исходного экспорта `hex` совпал с побайтовым округлением сохранённых чисел: `round(component × 255)`. Значение float32 `0.8999999761581421` даёт байт `229` и `E5`, хотя двойная точность `0.9` находится на границе округления к `230`. Сверяются сохранённые числа, а не литерал до float32.

Для этого образца получены три значения в разных путях: табличный и экспортный HEX `#1D2D6B`; CSS прямой заливки `#182E6F`; CSS-fallback переменной `#102F73`. Последнее расхождение исследовано в [Dev Mode](dev-mode-fallback.md).

DTCG определяет смысл `components` через `colorSpace`, а `hex` — как необязательный CSS sRGB-fallback. В проверенном P3-экспорте пространство каналов и смысл HEX не соответствуют такой интерпретации. [DTCG Color Module 2025.10](https://www.designtokens.org/tr/2025.10/color/#format).

## Приоритет полей при импорте

Контрольные переменные заранее заполнены RGBA `[0.03125, 0.0625, 0.125, 0.75]`. Импорт обновляет существующий режим. Неизменившееся значение вместе с уведомлением об ошибках обозначает пропущенную запись.

Таблица 1. Противоречивые поля в обоих профилях

| Ввод | Результат |
| :--- | :--- |
| `srgb`, P3-числа образца, `hex: #FF0000` | Сохранены числа образца; HEX таблицы `#1D2D6B` |
| `srgb`, `[1, 0, 0]`, `hex: #1D2D6B` | Сохранён `[1, 0, 0]`; HEX таблицы `#FF0000` |
| `srgb`, только `hex: #1D2D6B` | Запись пропущена |
| `$value: "#1D2D6B"` | Запись пропущена |
| Числа образца, `alpha: 0.25`, `hex: #1D2D6B80` | Сохранена альфа `0.25` |

`components` имеют приоритет над противоречивым HEX. Значения `alpha: 0` и `alpha: 0.25` сохранились; без `alpha` результат получил `1`. Дробные RGB-каналы сохранились в пределах float32, без округления до шестизначного HEX. Точные записи и ID находятся в [реестре тестов](../research/2026-10-15/variables-json/test-registry.json).

## Профиль документа и цвет

Исходный экспорт импортирован в документы с явно назначенными Display-P3 и sRGB. Все 57 итоговых записей совпали по RGB-числам и локальным ссылкам. fileKey документов различается.

Для `overlay-p3-hex` оба импорта сохранили `[29/255, 45/255, 107/255]` с точностью float32. В P3 эти числа означают исходный цвет, а в sRGB — цвет CSS HEX `#1D2D6B`. Разница двух интерпретаций составляет примерно `ΔEOK = 0.008733`, где L находится в диапазоне от 0 до 1. Это расчёт координат, а не измерение пикселей дисплея.

Для сохранения цветового смысла между профилями требуется преобразовать каналы до импорта. Одинаковый HEX в двух таблицах не доказывает равенство цвета. Проверенный native import такое преобразование не выполняет.

## Поддерживаемые и пропущенные записи

При исходных контрольных значениях в каждом профиле матрица дала уведомление **13 variables updated. Encountered errors importing 11 tokens**. Валидные RGB-записи и алиас обновлены; пропущенные записи сохранили контрольное значение.

Таблица 2. Пропущенные случаи

| Случай | Результат |
| :--- | :--- |
| `display-p3` с `components` | Пропущен |
| `display-p3` с `components` и HEX-fallback | Пропущен |
| `oklch` с `components` | Пропущен |
| `oklch` с `components` и HEX-fallback | Пропущен |
| `srgb-linear` с HEX-fallback | Пропущен |
| Неизвестное пространство `banana` с HEX-fallback | Пропущен |
| Отсутствующий `colorSpace` | Пропущен |
| Отсутствующие `components` | Пропущен |
| HEX-строка вместо объекта `$value` | Пропущен |
| RGB `[-0.1, 1.1, 0.5]` | Пропущен; clipping не выполнен |
| RGB с каналом `"none"` | Пропущен |

**Импорт `display-p3` с координатами float32 отдельно не проверялся.** В случаях `p3-components-only` и `p3-with-hex` использованы значения `[0.11372549019607843, 0.17647058823529413, 0.4196078431372549]`, полученные как `29/255`, `45/255`, `107/255` в двойной точности. Вариант с числами из экспорта Figma `[0.11372549086809158, 0.1764705926179886, 0.41960784792900085]` остаётся непроверенным. Результаты таблицы относятся к проверенному входному JSON.

Повторный импорт в P3 без сброса дал 9 обновлённых записей и 11 ошибок; после сброса контроля снова получены 13 обновлений и 11 ошибок. Счётчик обновлений зависит от предшествующих значений и не обозначает число поддерживаемых форматов.

HEX-fallback не включил импорт неподдерживаемого пространства. Поддержка `oklch(...)` в CSS-поле палитры не означает поддержку `colorSpace: "oklch"` в JSON-импорте.

Справка Figma перечисляет sRGB и HSL для цветовых токенов. Обновление существующего режима сопоставляет имена и типы. [Figma: Modes for variables](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables).

## Единицы HSL и обновление страницы

DTCG задаёт Hue в градусах от 0 до 360, S и L — в процентах от 0 до 100. [DTCG: HSL components](https://www.designtokens.org/tr/2025.10/color/#hsl).

Результаты пяти опытов совпали с обработкой нормализованных H, S и L. Это закономерность проверенных образцов; исходный код импортера не исследовался.

Таблица 3. HSL в обоих профилях

| `components` | RGB в экспорте сразу после импорта | HEX сразу | RGB после обновления |
| :--- | :--- | :--- | :--- |
| `[266, 50, 30]` | `[1480, 1480, 1480]` | `#5C2385C2385C238` | `[1, 1, 1]` |
| `[266, 0.5, 0.3]` | Примерно `[0.15, 0.15, 0.15]` | `#262626` | Те же дробные числа |
| `[266/360, 0.5, 0.3]` | Примерно `[0.28, 0.15, 0.45]` | `#472673` | Те же дробные числа |
| `[0, 0, 0.5]` | `[0.5, 0.5, 0.5]` | `#808080` | Те же числа |
| `[0, 0, 50]` | `[50, 50, 50]` | `#31CE31CE31CE` | `[1, 1, 1]` |

В файл записано десятичное значение `266/360`, а не выражение. До обновления выполнен штатный экспорт без промежуточного чтения через Plugin API. JSON содержит числа `1480` и `50`: длинный HEX не является одним лишь дефектом отображения таблицы.

После обновления повторный экспорт сохранил `[1, 1, 1]` и `#FFFFFF` для двух выходящих за диапазон результатов. RGB-импорт с выходящими за диапазон числами, напротив, пропустил запись. Эти пути проверяются отдельно.

Нормализованный HSL даёт ожидаемые RGB-числа на проверенном фиолетовом образце, но не соответствует единицам DTCG. Для переноса стандартных токенов используется предварительное преобразование в RGB целевого профиля.

## Алиасы, имена и ID

Экспорт сохраняет ссылки вида `$value: "{primitive.overlay}"`. Импорт в подготовленную коллекцию сохранил цепочку `role/overlay`, `semantic/overlay`, `primitive/overlay` и заменил ссылки исходными именами на локальные ID целевого файла. Алиасы не превратились в HEX-литералы.

ID обновляемых целевых переменных сохранились. Контрольная запись с чужим `com.figma.variableId: "VariableID:31:3"` обновила переменную со своим именем, оставив её целевой ID. В реестре используется пара **fileKey и variableId**: одинаковые локальные ID встречаются в двух документах.

Имя `P3 values` в импортируемом экспорте не переименовало существующий целевой режим `Mode 1`. Прогон изучает обновление режима, а не создание режима перетаскиванием файла.

## Преобразование между кодом и JSON

Для кода `components` интерпретируются по проверенному профилю исходного документа. В P3-файле эти числа передаются в `color(display-p3 ...)`, несмотря на метку `srgb` native-экспорта. HEX из таблицы сохраняет меньше информации.

Для стандартного DTCG-представления P3-экспорта требуется указать `colorSpace: "display-p3"`, сохранить P3-каналы и вычислить CSS sRGB-fallback с выбранной политикой охвата. Проверенный native import Figma отклоняет такой P3-объект.

Для native JSON-импорта в P3-документ вычисляются P3-каналы из исходного OKLCH, затем эти числа передаются в поддерживаемый объект с `colorSpace: "srgb"`. Это обход наблюдённого поведения, а не стандартная маркировка P3-цвета. Файл сопровождается явным указанием целевого профиля. HEX-fallback не исправляет неправильные `components`.

Для sRGB-документа вычисляются sRGB-каналы; метка `srgb` тогда соответствует числам. Цвет вне охвата требует выбранного gamut mapping или clipping до импорта. Проверенный RGB-импорт сам clipping не выполнил.

## Повторение и границы проверки

Чтобы повторить прогон:

1. Откройте [отчёт](../research/2026-10-15/variables-json/README.md).
2. Импортируйте нужную локальную `.fig` в Figma.
3. Проверьте профиль через **File color profile**.
4. Восстановите контрольные значения коллекции по `seed-config.json`.
5. Выберите **Import mode** в контекстном меню существующего режима.
6. Выберите JSON из `imports` или извлечённый JSON экспорта.
7. Сохраните уведомление, таблицу и JSON до обновления страницы.
8. Обновите страницу.
9. Сохраните повторный экспорт и числовой снимок с ID переменных.

**Export modes** в проверенных коллекциях с одним режимом скачивает ZIP с JSON режима. Импорт выполнен из извлечённого `.tokens.json`; прямой импорт ZIP не проверялся. Системные **Save**, **Open** и **Replace** выполнены через computer-use.

`npm run verify:variables` и GitHub Actions проверяют архив и расчёты, не выполняя живой импорт. Новый прогон сохраняется отдельно с версиями среды и соответствием ID.

Для сброса подготовлен [reset-variable-import-fixtures.js](../scripts/figma/reset-variable-import-fixtures.js). Функция применяется к выбранной коллекции тестовой копии с `sentinel` из `seed-config.json`. Контрольные числа задаются через Plugin API: ввод округлённого HEX `081020` не воспроизводит точный RGBA исходного контроля. Функция выполнена в P3-файле при контрольном повторении импорта.

Проверены COLOR-переменные, локальные алиасы и обновление существующих режимов. Создание переменных перетаскиванием JSON, несколько режимов в одной коллекции, библиотечные ссылки и другие типы токенов в прогон не входят. Новые `.fig` проверены по структуре ZIP, CRC и SHA-256; их обратный импорт в этом прогоне не повторялся.
