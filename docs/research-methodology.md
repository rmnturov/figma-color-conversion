# Методика повторной проверки

Методика проверяет перенос цветов между кодом и Figma и генерацию резервных значений в Dev Mode. Проверка расчётной модели и проверка текущего интерфейса выполняются отдельно.

## Область и гипотезы

Основная область: непрозрачные SOLID-заливки, COLOR-переменные, документ Display-P3, локальные алиасы и браузерный Dev Mode.

Таблица 1. Гипотезы исследования

| Код | Гипотеза | Различающий опыт |
| :--- | :--- | :--- |
| F1 | Прямая заливка и переменная имеют одинаковый HEX-fallback | Одинаковые RGB-каналы, разные способы привязки |
| F2 | HEX-fallback переменной совпадает с двумя проходами P3 в sRGB | Сравнение с моделью, включающей clipping и промежуточное округление |
| F3 | Каждый алиас добавляет преобразование | Примитивная переменная и цепочка из двух алиасов |
| R1 | Для HEX-поля P3-документа подходит sRGB HEX | Ввод sRGB HEX и чтение сохранённых P3-каналов |
| R2 | Для HEX-поля подходит P3 HEX | Ввод байтов P3 и сравнение с исходным OKLCH |
| R3 | CSS-поле переменной сохраняет точность OKLCH | Ввод OKLCH, чтение RGBA, обновление страницы и повторное чтение |
| G1 | Цвет вне P3 обрезается по каналам | Контроль, где clipping и gamut mapping дают разные результаты |
| T1 | Исходная запись OKLCH сохраняется в Dev Mode | Сравнение CSS до и после обновления страницы |

Все гипотезы имеют указанный предел проверки. Результат шести контрольных цветов не является доказательством для всех цветов, экспортов и версий Figma.

## Подготовка прогона

Чтобы подготовить новый прогон:

1. Создайте тестовый файл Figma или выделите отдельную тестовую область в существующем файле.
2. Установите профиль **Display P3** через UI файла. Для нового файла различие **Assign** и **Convert** нужно зафиксировать в отчёте.
3. Сохраните снимок меню **File color profile** с выбранным профилем.
4. Запишите дату, часовой пояс, ключ файла, ID страницы, версию браузера, ОС, Node.js и расчётной библиотеки.
5. Зафиксируйте состояние файла до создания образцов: страницы, коллекции, режимы и целевые узлы.
6. Создайте каталог нового прогона, например `research/2026-11-01/run-01`.
7. Сохраните параметры прогона в `metadata.json`.

Архив от 14.10.2026 сохраняется как исходный результат. Версии браузера и сборки Figma для этого прогона не записаны; их отсутствие обозначено `null`.

Исследование проводится на тестовых объектах. Смена профиля рабочего документа или обновление чужих переменных не требуется для повторения опытов.

## Создание прямых образцов

Для повторного прогона на исходных слоях можно сначала [восстановить локальный `.fig`](local-figma-copy.md). [Каталог тестов](test-catalog.md) и машиночитаемые реестры сохраняют все ID и пути. Создание новых образцов нужно, если требуется новый независимый набор; их ID записываются отдельно.

Контрольный набор задан в [cases.json](../research/2026-10-14/cases.json). Числа RGB относятся к Display-P3. Строка `thread` рассчитана из `oklch(84% 0.08 17)`, а не из sRGB HEX.

Чтобы создать прямые образцы:

1. Откройте тестовую страницу.
2. Выполните [шаблон создания образцов](../scripts/figma/create-forward-fixtures.js) в контексте Figma Plugin API.
3. Сохраните возвращённые ID узлов, переменных, коллекции и режима.
4. Прочитайте значения COLOR-переменных и привязки заливок после создания.
5. Сверьте исходные RGB-каналы у прямой заливки, примитивной переменной и роли с двумя алиасами.

Шаблон экспортирует функцию `createForwardFixtures(figma, parameters)`. В плагине функция вызывается после загрузки модуля. Для `use_figma` декларация функции передаётся без `export`, затем добавляется `return await createForwardFixtures(figma, parameters)`. Перед вызовом инструмента применяются актуальные инструкции навыка `figma-use`.

Функция использует стандартные методы Plugin API и возвращает созданные ID. `getCSSAsync` в исходной MCP-интеграции был недоступен, поэтому вывод Dev Mode собирался через UI.

Для сбора каналов подготовлен [read-state.js](../scripts/figma/read-state.js). Функция `readColorState(figma, { rootId, profile: 'p3' })` сохраняет заливки, режимы потребителей, цепочки алиасов и разрешённое значение отдельно для каждого узла. Профиль передаётся после проверки через UI. Шаблоны функций адаптированы для повторного использования при упаковке репозитория; сам архив исходного прогона получен инструментальными вызовами, описанными выше.

## Сбор CSS через браузер

Чтобы собрать данные Dev Mode:

1. Откройте слой по его ID в браузере.
2. Включите **Dev Mode**.
3. Выберите **Code** и язык **CSS** в панели свойств.
4. Проверьте имя выбранного слоя.
5. Дождитесь заполнения блоков **Layout** и **Style**.
6. Сохраните CSS из **Style**, включая sRGB-fallback и P3-строку.
7. Сохраните снимок выбранного слоя и читаемой панели CSS.
8. Повторите действия для оставшихся образцов.

Наличие заголовка выбранного слоя ещё не доказывает загрузку CSS. В исходном прогоне блок CSS одного слоя появился позже заголовка; пустое наблюдение было повторно прочитано и заменено заполненным до сохранения архива.

Для автоматизации используются документированные UI-действия и DOM-снимки. Модель или вывод MCP, сгенерированный вместо браузерного CSS, не заменяет наблюдение Dev Mode.

Формат записи одного наблюдения:

```json
{
  "id": "ID_FROM_FIGMA",
  "name": "overlay-variable",
  "css": [
    "width: 256px;height: 100px;",
    "background: var(--primitive-overlay, #102F73);background: var(--primitive-overlay, color(display-p3 0.1137 0.1765 0.4196));"
  ],
  "snapshot": "DOM-снимок выбранного слоя и панели"
}
```

## Сопоставление прямого вывода

Чтобы сравнить результаты:

1. Преобразуйте исходные P3-каналы в sRGB библиотекой зафиксированной версии.
2. Рассчитайте вариант одного прохода с clipping и округлением.
3. Рассчитайте вариант двух проходов с промежуточным округлением и повторной интерпретацией байтов как P3.
4. Сравните оба варианта с CSS каждого слоя.
5. Сопоставьте результат примитивной переменной и роли с алиасами.
6. Сохраните вычисленные каналы и итоговые HEX.

Результат F2 обозначается численной моделью, согласованной с наблюдениями. Для утверждения о внутреннем коде Figma нужны дополнительные источники или доступ к реализации.

## Проверка обратного ввода

Чтобы проверить создание переменной из цвета в коде:

1. Создайте отдельную коллекцию в документе Display-P3.
2. Создайте COLOR-переменные для P3 HEX, sRGB HEX и CSS OKLCH каждого исходного цвета.
3. Вставьте рассчитанные HEX в поля значений двух переменных.
4. Откройте цветовой образец третьей переменной.
5. Выберите **CSS** в **Color format**.
6. Вставьте исходный `oklch(...)` в **Color**.
7. Нажмите клавишу Enter.
8. Закройте палитру.
9. Сохраните снимок значений и прочитайте RGBA через Plugin API.

После этого выполняется отдельная проверка сохранения:

1. Обновите страницу браузера.
2. Проверьте значения в интерфейсе.
3. Повторно прочитайте RGBA через Plugin API.
4. Сравните каналы до и после обновления.
5. Преобразуйте сохранённые каналы из P3 в OKLCH и вычислите ΔEOK относительно исходного цвета.
6. Сохраните исходные и вычисленные значения вместе с ID переменных.

В исходном прогоне для HEX-ввода проверялись байты, делённые на 255, с допуском `2e-7` на канал. Для CSS-ввода внутри P3 проверялись расчётные дробные P3-каналы с тем же допуском. Допуск служит проверке float32 в этом опыте и не является универсальным порогом визуального совпадения.

## Проверка охвата и временной формы

Чтобы проверить цвет вне охвата P3:

1. Выберите исходный цвет, для которого clipping и выбранный gamut mapping дают разные результаты.
2. Рассчитайте оба варианта с зафиксированной версией библиотеки.
3. Введите исходный OKLCH в CSS-поле переменной.
4. Прочитайте сохранённые RGBA.
5. Сопоставьте каналы с обеими гипотезами.

В исходном прогоне использован `oklch(70% 0.4 145)`: clipping дал P3 HEX `#00CE00`, а `Color.js 0.5.2` с `method: "css"` — `#00C700`.

Чтобы проверить временное сохранение CSS-нотации:

1. Введите OKLCH в CSS-поле прямой SOLID-заливки.
2. Сохраните вывод Dev Mode до обновления страницы.
3. Обновите страницу без промежуточных вызовов MCP.
4. Сохраните вывод Dev Mode после обновления.
5. Прочитайте сохранённые RGB-каналы отдельно от представления CSS.

Эта проверка различает сохранение цвета и сохранение текстового формата. Исходный опыт показал правильный цвет и изменение текстового представления после обновления.

## Критерии и архив

Новый прогон завершён, когда для заявленного набора есть:

- Подтверждённый профиль файла и режимы переменных.
- Исходные каналы и цепочки алиасов.
- CSS выбранных слоёв из браузерного Dev Mode.
- Результаты HEX-ввода и CSS-ввода до и после обновления.
- Снимки, по которым различимы выбранный слой и значения.
- Расчёты, версии зависимостей и явные пределы выводов.

Проверка архива не требует доступа к Figma. Чтобы выполнить её:

1. Установите зависимости командой `npm ci`.
2. Выполните `npm run verify`.
3. Выполните `npm test`.
4. Выполните `npm run check:links`.

Для сохранённой локальной копии дополнительно выполните `npm run verify:copy`. Команда проверит SHA-256 `.fig` и архив обратного импорта. Живые действия в Figma повторяются отдельно.

Новые результаты сохраняются в отдельном каталоге. Изменение вывода Figma фиксируется как расхождение с прежним прогоном, а не как повод перезаписать прежние доказательства. Для каждого расхождения указываются профиль, слой, режим, новые значения и шаг, на котором изменилось поведение.

Практическая проверка растрового экспорта, альфы через HEX, библиотечных алиасов, градиентов и экранного color management требует расширения матрицы опытов.
